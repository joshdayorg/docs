## The Real Interface

In Module 3, you set up remote access through a browser. That works, but it still feels like using a tool. You open a URL, type in a box, wait for a response.

What if you could just... text your AI? Open Messages on your iPhone, tap a conversation, and send it a message like you would to a friend? No app, no browser, no URL to remember.

That's what iMessage integration gives you. Your AI becomes a contact in your Messages app. You text it. It texts back. From your lock screen, from Siri, from anywhere you can send a message.

This is the module where your AI stops feeling like software and starts feeling like a partner.

## How It Works

OpenClaw talks to iMessage through a macOS helper app called [BlueBubbles](https://bluebubbles.app). Here's the flow:

```
Your iPhone (Messages app)
        ↓
   iCloud / iMessage relay
        ↓
   Messages.app on your Mac
        ↓
   BlueBubbles server (watches for new messages)
        ↓
   OpenClaw Gateway (processes + responds)
        ↓
   BlueBubbles → Messages.app → your iPhone
```

BlueBubbles runs alongside Messages on your Mac and acts as a bridge. When a message arrives, BlueBubbles tells OpenClaw. When OpenClaw responds, BlueBubbles sends it through Messages. Your iPhone sees it as a normal iMessage conversation.

<Note>
This requires a Mac that stays on and is signed into iMessage. If your OpenClaw gateway runs on Linux, you'll need a Mac somewhere on your network for the iMessage bridge. Other messaging options (Telegram, WhatsApp, Signal) don't have this requirement and work on any OS.
</Note>

## What You Need

- **A Mac** running macOS Sequoia (15) or newer, signed into iMessage
- **BlueBubbles server** installed on that Mac
- **OpenClaw** running (from Module 2)
- **10 minutes** for setup

The Mac running BlueBubbles can be the same machine running your OpenClaw gateway, or a different one. Same machine is simpler.

## Step 1: Install BlueBubbles

BlueBubbles is a free, open-source macOS app that gives your iMessage setup a REST API.

<Steps>
  <Step title="Download BlueBubbles">
    Go to [bluebubbles.app/install](https://bluebubbles.app/install) and download the macOS server.
  </Step>
  <Step title="Install and open it">
    Drag BlueBubbles to your Applications folder and open it. Follow the setup wizard.
  </Step>
  <Step title="Enable the Web API">
    In BlueBubbles settings, enable the local REST API. Set an API password. You'll need this password for OpenClaw.
  </Step>
  <Step title="Note the server URL">
    BlueBubbles shows its local address, something like `http://192.168.1.100:1234`. Write this down.
  </Step>
</Steps>

<Tip>
If BlueBubbles asks about Firebase or Google Cloud setup, that's for their mobile app push notifications. You don't need it for OpenClaw. The local REST API is all that matters.
</Tip>

## Step 2: Grant macOS Permissions

This is the step that trips up most people. macOS protects your Messages data behind several permission gates. You need to approve them all.

### Full Disk Access

BlueBubbles needs to read the Messages database. Without Full Disk Access, it can't see your messages.

<Steps>
  <Step title="Open System Settings">
    Go to **System Settings > Privacy & Security > Full Disk Access**.
  </Step>
  <Step title="Add BlueBubbles">
    Click the **+** button and add the BlueBubbles app from your Applications folder. Make sure the toggle is ON.
  </Step>
  <Step title="Add your terminal (if running OpenClaw from terminal)">
    If you launch OpenClaw from Terminal or iTerm, add that app too. This ensures the OpenClaw gateway process inherits Full Disk Access.
  </Step>
</Steps>

### Automation Permission

When BlueBubbles first tries to send a message through Messages.app, macOS will pop up an Automation permission prompt. **You must click Allow.**

<Warning>
If you miss this prompt (it can appear behind other windows), sending will silently fail. If messages aren't going out, check **System Settings > Privacy & Security > Automation** and make sure BlueBubbles has permission to control Messages.
</Warning>

### The FDA Gotcha

Full Disk Access is the number one support issue with iMessage integration. Here's what makes it tricky:

- macOS grants FDA per-process. If you start OpenClaw from a different terminal app, you might need to grant FDA again.
- LaunchAgent daemons run in their own context. If OpenClaw starts on boot via a LaunchAgent, the daemon process needs FDA too.
- SSH sessions have their own context. If you SSH into your Mac and run OpenClaw, you may need to grant FDA to the SSH process.

**The fix:** Run an interactive command once in whatever context will be running OpenClaw. This forces the permission prompt:

```bash
# If using the legacy imsg CLI:
imsg chats --limit 1
```

If a macOS dialog pops up asking for access, click Allow. After that, the background process will inherit the permission.

## Step 3: Configure OpenClaw

Now tell OpenClaw about your BlueBubbles server. The easiest way is through the onboarding wizard:

```bash
openclaw onboard
```

Select BlueBubbles when prompted, and enter:

- **Server URL**: The BlueBubbles server address (e.g., `http://192.168.1.100:1234`)
- **Password**: The API password you set in BlueBubbles
- **DM policy**: Choose `pairing` (recommended, we'll explain why in a moment)

If you prefer to configure it manually, edit your config:

```bash
nano ~/.openclaw/openclaw.json
```

Add the BlueBubbles channel:

```json
{
  "channels": {
    "bluebubbles": {
      "enabled": true,
      "serverUrl": "http://192.168.1.100:1234",
      "password": "your-bluebubbles-password"
    }
  }
}
```

Then restart the gateway:

```bash
openclaw gateway restart
```

<Note>
Replace the server URL and password with your actual values. If BlueBubbles and OpenClaw are on the same Mac, the URL is usually `http://localhost:1234` (check BlueBubbles settings for the exact port).
</Note>

## Step 4: Set Up Webhooks

BlueBubbles needs to know where to send incoming messages. You'll point it at your OpenClaw gateway.

In BlueBubbles settings, add a webhook:

- **URL**: `http://127.0.0.1:18789/bluebubbles-webhook?password=your-bluebubbles-password`
- **Events**: All message events

If your gateway is on a different machine than BlueBubbles, use the gateway's IP or Tailscale hostname instead of `127.0.0.1`.

<Accordion title="Using Tailscale between BlueBubbles and OpenClaw">
  If BlueBubbles runs on a Mac Mini and your gateway runs on a Linux server, connect them via your Tailscale network from Module 3:

  ```
  http://your-gateway.tailnet-name.ts.net:18789/bluebubbles-webhook?password=your-password
  ```

  Or use the Tailscale IP directly:

  ```
  http://100.x.x.x:18789/bluebubbles-webhook?password=your-password
  ```
</Accordion>

## Step 5: Send Your First Message

Restart the gateway to pick up the new config:

```bash
openclaw gateway restart
```

Check that the channel is connected:

```bash
openclaw channels status
```

You should see BlueBubbles listed as active. Now open Messages on your iPhone and send a text to your Mac's iMessage address (the email or phone number signed into Messages on the Mac running BlueBubbles).

The first time you message, you'll get a **pairing code** back instead of a real response. That's the security system working as intended.

## Step 6: Approve Your Pairing

OpenClaw uses a pairing system to control who can talk to your AI through iMessage. This is important because anyone who has your iMessage address could potentially text your AI. You don't want random people controlling your assistant.

When you first text your AI, it replies with something like:

> "To pair with this assistant, provide this code to the owner: **ABCD1234**"

Now approve yourself from the terminal:

```bash
openclaw pairing list bluebubbles
```

This shows pending pairing requests with their codes. Find yours and approve it:

```bash
openclaw pairing approve bluebubbles ABCD1234
```

That's it. Send another message from your iPhone. This time, your AI responds for real.

<Tip>
You only need to pair once per phone number or iMessage address. After approval, you're permanently on the allow list. If someone else texts your AI and you don't approve their code, they'll never get a response.
</Tip>

## DM Policies: Who Can Talk to Your AI?

The `dmPolicy` setting controls how your AI handles incoming messages from new contacts:

| Policy | Behavior |
|--------|----------|
| `pairing` | Unknown senders get a code. You approve or ignore. **(Recommended)** |
| `allowlist` | Only pre-approved contacts can message. Everyone else is silently ignored. |
| `open` | Anyone can message your AI. No approval needed. |
| `disabled` | iMessage DMs are completely off. |

Start with `pairing`. It's the right balance of security and convenience. You can pre-approve contacts too:

```json
{
  "channels": {
    "bluebubbles": {
      "dmPolicy": "allowlist",
      "allowFrom": ["+15555550123", "friend@icloud.com"]
    }
  }
}
```

<Warning>
Never set `dmPolicy: "open"` unless you truly want anyone with your iMessage address to have full access to your AI and its tools. Your AI can read files, run commands, and access your data. Treat DM access like giving someone the keys to your computer.
</Warning>

## Group Chats

Your AI can participate in iMessage group chats too. By default, group access is set to `allowlist`, meaning the AI only responds in groups where an approved sender triggers it.

To enable groups:

```json
{
  "channels": {
    "bluebubbles": {
      "groupPolicy": "allowlist",
      "groupAllowFrom": ["+15555550123"],
      "groups": {
        "*": { "requireMention": true }
      }
    }
  }
}
```

With `requireMention: true`, your AI only responds in groups when someone mentions it by name. This prevents it from jumping into every conversation. Set mention patterns in your agent config under the agent's entry in `agents.list`:

```json
{
  "agents": {
    "list": [
      {
        "id": "main",
        "default": true,
        "groupChat": {
          "mentionPatterns": ["@ai", "@assistant", "hey ai"]
        }
      }
    ]
  }
}
```

You can also set a global fallback under `messages.groupChat.mentionPatterns`, but the per-agent path is the correct primary location.

## Advanced Features

BlueBubbles gives your AI some nice iMessage-native capabilities:

- **Tapback reactions**: Your AI can react to messages with thumbs up, hearts, etc.
- **Typing indicators**: The other person sees the typing bubble while your AI is thinking.
- **Read receipts**: Your AI marks messages as read.
- **Reply threading**: Your AI can reply to specific messages in a thread.
- **Message effects**: Send messages with effects like "slam" or "invisible ink."

These are enabled by default. You can toggle them in config:

```json
{
  "channels": {
    "bluebubbles": {
      "sendReadReceipts": true,
      "actions": {
        "reactions": true,
        "reply": true,
        "sendWithEffect": true
      }
    }
  }
}
```

## Alternative: Legacy imsg CLI

OpenClaw also supports a lighter-weight iMessage integration through the `imsg` CLI tool. This is the older approach and still works, but BlueBubbles is recommended for new setups because it has richer features (reactions, typing indicators, easier webhook setup).

If you want the simpler option:

```bash
brew install steipete/tap/imsg
```

<Note>
The `imsg` tap above may change over time. Check the [OpenClaw docs](https://docs.openclaw.ai) for the latest install instructions if the tap isn't found.
</Note>

Then configure:

```json
{
  "channels": {
    "imessage": {
      "enabled": true,
      "cliPath": "/usr/local/bin/imsg",
      "dbPath": "~/Library/Messages/chat.db"
    }
  }
}
```

The `imsg` approach requires the same Full Disk Access permissions. The main tradeoff: simpler setup, fewer features. No typing indicators, no reactions, no webhooks.

## Keeping It Running

Your AI is only reachable via iMessage when both OpenClaw and BlueBubbles are running. Here's how to make sure they survive reboots:

**OpenClaw**: If you used `--install-daemon` during setup (Module 2), it already starts on boot. Verify:

```bash
openclaw gateway status
```

**BlueBubbles**: Configure it to launch on login. In BlueBubbles settings, enable "Start on Login" or add it to your Login Items (System Settings > General > Login Items).

**Messages.app**: On some setups (especially VMs or headless Macs), Messages can go idle and stop processing incoming messages. If you notice messages not arriving, the fix is a small LaunchAgent that pokes Messages every few minutes to keep it alive. See the OpenClaw docs for the script.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Messages aren't arriving / AI doesn't respond">
    Check the chain step by step:

    1. Is BlueBubbles running? Open it and check its status.
    2. Is the webhook configured? BlueBubbles should show your OpenClaw webhook URL.
    3. Is OpenClaw running? `openclaw gateway status`
    4. Is the channel active? `openclaw channels status`
    5. Are you paired? `openclaw pairing list bluebubbles` to check if your number is approved.

    If everything looks good but messages still aren't flowing, check the gateway logs:

    ```bash
    openclaw logs
    ```
  </Accordion>

  <Accordion title="AI responds in the dashboard but not via iMessage">
    The gateway is working, but the iMessage channel isn't connected. Check:

    - BlueBubbles is running and the webhook points to the right URL
    - The password in your OpenClaw config matches the BlueBubbles API password
    - The gateway port in the webhook URL matches your actual gateway port (default 18789)
  </Accordion>

  <Accordion title="Full Disk Access not working">
    FDA must be granted to the exact process that's reading the Messages database. If you changed how you launch OpenClaw (different terminal, SSH, LaunchAgent), you may need to grant FDA again.

    Go to **System Settings > Privacy & Security > Full Disk Access** and make sure all relevant apps are listed and toggled ON:

    - BlueBubbles
    - Terminal / iTerm (if you launch OpenClaw from terminal)
    - Node.js (sometimes needs to be added explicitly)

    After granting FDA, restart both BlueBubbles and OpenClaw.
  </Accordion>

  <Accordion title="Pairing code not arriving">
    Pairing codes expire after 1 hour, and OpenClaw limits pending requests to 3 per channel. If you've been testing a lot:

    ```bash
    openclaw pairing list bluebubbles
    ```

    Clear old requests and try again. Also check that `dmPolicy` is set to `"pairing"` (not `"disabled"` or `"allowlist"` with an empty list).
  </Accordion>

  <Accordion title="Sending works but receiving doesn't (or vice versa)">
    This is usually a permissions issue. Sending requires **Automation** permission (BlueBubbles controlling Messages.app). Receiving requires **Full Disk Access** (reading the Messages database).

    Check both in System Settings > Privacy & Security.
  </Accordion>
</AccordionGroup>
